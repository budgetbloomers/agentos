## Non-negotiables (violating these is a bug)

1. **NBA math is deterministic code, never LLM arithmetic.** The dashboard's `acStats`/`cfTier`/`acNBA`/`acComposite` functions are the engine. Agents may EXPLAIN scores; only code COMPUTES them. When scoring outside the dashboard, write and run a script.
2. **One primary NBA per agent** — ladder walked in fixed order P1·R1 → P4·R10, first trigger wins. R2A-1 is a flag/footnote, never a primary NBA.
3. **R2A tier = HIGHER of count band and rate band.** One capped penalty per tier (`pen1`/`pen2`/`pen3` in the `nbaThresholds` rule — live-editable; the cap is `pen3`). Never the retired −3-per-*fail* v2.5 logic: the penalty is a tier value, never accumulated per fail. **Since 2026-09-11 every penalty is 0 in BOTH engines (Nick: "nba priority rules must not affect the agent scores")** — Ops `pen1/2/3` default 0, PULSE `r2aTiers[].penalty` 0 with a dated `_changes[]` entry in specs/composite_rules.json. The tier still classifies, still travels to every card, still decides Elite; it never moves a score.
4. **Composite is the `compositeWeights` rule** — Value/Volume/QA/GWP %ile/Conversion/Talk/Attendance, in that priority order (value first, then volume, then quality); weights are live-editable and renormalise across the metrics an agent actually has. Penalty applied AFTER the sum ('Adj') — and it is 0 since 2026-09-11, so Adj equals the composite (see 3). Cancellations and attempts-per-lead are diagnostics — never scored.
5. **Tenure-relative everything.** Never compare agents across tenure groups (M1/M2/EXP–Courtesy/EXP–Cuddle). GWP percentile within group only.
6. **One money model: Power BI - Active Cases** (specs/AgentOS-v3.8-upload-frameworks.md §2). GWP = Σ Charge Amount per account, charges are EX-VAT, grossed up ×(1+vatRate rule, default 15%, zero-safe) to inclusive; sale dated per row's Contract Create Date; agent matched on Owner. Monthly uploads ACCUMULATE — a re-upload replaces only its own date span (deliberate deviation from pack R-ING-BI-06). There is NO legacy fallback: with no BI file loaded, money reads blank and says so. The old Activated-Services + GWP-table pricing was removed 2026-07; never reintroduce it silently. **An absence is not a nought, and this now runs the whole way through the scoring**: with no BI file, `acStats` returns null (not 0) for Target Achievement, Conversion and sales-per-day, `applyGroupPercentiles` returns null for the GWP percentile, and `acComposite` renormalises across the metrics the agent actually has — so no team's composite silently drops ~30 points and the NBA ladder does not report a floor-wide "Critical Sales-Volume Failure" over a missing upload. An agent who genuinely sold nothing WITH a BI file loaded still scores 0 and still fires the ladder. Guarded by `diagnostics/verify-ops-no-bi.mjs` (10 checks, both directions). The same doctrine governs PULSE's `perfScore`: a driver with no data leaves the denominator and the rest renormalise to 100 — never an imputed value (QA used to be filled in at 80%, so an agent evaluated at a real 70% ranked below one nobody had evaluated) and never a zero. A real 0% QA still scores zero, because the rule book is explicit that a zero is an outcome. `perfParts` publishes the EFFECTIVE weight, so Agent Analytics' rating card still adds up. Guarded by `diagnostics/verify-perf-score.mjs` (10 checks).
7. **CB codes normalise**: `CB-15` = `CB15` = `cb 15` (see `normCB`). The daily Agent List is the identity base — every cross-source join resolves through it. Unmapped rows are FLAGGED, never silently dropped or invented.
8. **KB response contract**: label every figure actual/model/proposed/historical; `[INPUT REQUIRED]` for missing facts, never invent; flag conflicts (330 vs 370 agents, R42,500 vs R34,762 rev/agent, etc.) per module 10 treatments; never call seat contribution "EBITDA" before management-account tie-out.
9. **Names**: Nicholas Pillay = CTTO (never "Chief Growth..."); Claudell Panday (spelling); Abigail owns recruitment execution; COO unresolved unless kb-state.md records signed evidence.
10. **PII**: masking defaults ON. The suite sits behind its own login (worker/src/auth.mjs — PBKDF2 + sessions + lockout; auth-gate.js on every page). Cloudflare Access remains an optional outer wall, not the only lock.
11. **History is attributed to the org as it stood — at MONTH grain, and the Agent List owns the current month.** Facts read `orgAt(code, date)` — the effective-dated `S.orgHist` — never `S.roster`, which is a live snapshot with no effective date and so is the wrong answer for every past day. **The list wins its whole month (Nick, 2026-08-27, third request: "when the agent list is updating, it needs to update all the time"):** a roster ingest calls `recordOrgList`, which REWRITES the agent's segments inside the list's own month (segment lands on the month boundary; a new intake keeps their first-sighting date) and leaves every other month — earlier AND later — untouched, so a mover reads the new TL/campaign for the whole current month the moment the list lands. Cross-month attribution is unchanged: Month 1 keeps its leader when the agent moves in Month 2. The tracker daily sheet still files day-dated history through `recordOrg`; a later list collapses it only within its own month. A snapshot is stamped with the date it describes (`rosterAsOf`: the Data tab's "effective from", else a date in the filename, else today) — the override now picks WHICH month the list wins. Dates before the earliest observation resolve to that earliest segment. Placeholder carve-outs survive: a "TBC"/blank TL never erases a real leader, and a first REAL assignment back-dates over an all-placeholder history (`provisionalTL`). `M.agents[].tl` is the period's leader and `tlNow` the current one; `M.tlMoved` names the difference (now only cross-source/cross-month). Guarded by `diagnostics/verify-history.mjs` (39 checks) + `verify-tbc-backdate.mjs` (9). The Agent List also SYNCS across apps: uploads land in the VAS Upload Station; the Worker's `/api/roster` serves PULSE's roster with a change-fingerprint, and AgentOS Analytics re-ingests it through its own `applyLoad` on boot + every 10 min (`syncRosterFromVAS`) — never edit one app's roster store by hand. Every OTHER export relays as the RAW FILE, never derived rows (PULSE aggregates at ingest, so derived rows would strip QA coaching categories / per-call rows / BI charge detail), and the relay is BIDIRECTIONAL — an upload in EITHER station reaches the other app: PULSE's `archiveUpload` and AgentOS's `archiveForVAS` post ingested bytes to the Worker (`/api/upload-archive`, 30 MB cap, `kv:upload-manifest`); AgentOS `syncUploadsFromVAS` pulls unseen files through its own readUpload → detectSource → applyLoad, and PULSE `syncUploadsFromStation` feeds them to its own `handleFiles`. No ping-pong: both archivers check the manifest hash before posting. Each manifest file is decided ONCE per app (`state.syncedUploads` in cb-config / `S.relaySeen` in vas-state); AGENT_LIST skips the Ops-side relay (it flows via `/api/roster`), SES_* never travels; unrecognised formats (MTD tracker, manual stats) are skipped by design. **A CAMPAIGN MOVE IS SPLIT BY DATE (sprint 2026-09-29, decision D4 — decided by Aarav for Nick, Nick to confirm):** the whole-month rule above still holds for the TEAM LEADER and for which campaign an agent is on NOW, but a genuine campaign move inside a month no longer blends — UAT found four Download & Test → Courtesy movers reported as one month. The Worker's `GET /api/campaign-moves?month=` (`worker/src/moves.mjs`) derives each mover's dated campaign segments from the dated `agent_list` snapshots (the move takes effect on the first snapshot showing the new campaign; an admin can state the true day in `kv:campaign-move-overrides` via `POST /api/campaign-moves`); a Nesting → X graduation is a phase change, not a move (`PHASE_CAMPAIGNS`). PULSE splits the mover's facts by those segments, the digest row is the SUM of the month with `segments[]` per campaign, campaign blocks count a mover once per campaign, and the campaign-manager scope reads one row per segment (`bySegment`). Commission per campaign plan is a labelled PROJECTION on the agent's page until Nick/finance confirm how a split month is paid. Guarded by `diagnostics/verify-campaign-moves.mjs` + `verify-campaign-split.mjs`.
12. **VAS MTD maths comes from the rule book, not from judgement.** `specs/mtd_engine_rules.json` (Appendix A of the VAS MTD Reporting Engine spec v6.0) is the record; the operative subset is inlined in `nicks_code/index.html` as `MTD_RULES` because the app must run from `file://`. **Change both together** — `diagnostics/verify-engine-rules.mjs` fails on drift. The rules that most often look like bugs and are not: Courtesy/Nesting Actual Shifts are DIALLER-derived (talk>0 → 1) while Cuddle uses the HR register; dialling days come from the attendance register, not from every dated file; QA filters on Date of Call ONLY, keeps 0% scores, and totals as a mean of agent means; CB67/CB205/CB265 are excluded by a maintained list that no data rule reproduces; ViciDial's `EXPORT_CALL_REPORT` (tab-separated .txt, one row per call) bills talk time as Σ`length_in_sec` grouped on the **`user`** column — the agent's CB number, never `owner`, which is blank on over half the rows — and that includes ringing, ~38% of the total, deliberately (Nick, 2026-08-13), reported on every upload and switchable via `viciCallReport.talkFrom`. V01–V22 re-run on every upload and print on the Data tab — never ship a figure with an error-severity FAIL. **A rule must be READ, not copied**: every gross-up goes through `MTD_VAT`, derived from `MTD_RULES.vat`, because the literal 1.15 scattered through the engine meant the VAT rule was drift-checked against the spec and used by nothing — editing it in both places would have passed every guard and moved not one rand. `diagnostics/verify-rule-constants.mjs` fails if any calculation grows its own copy again, and also holds the anonymous peer group to Σsales ÷ Σtarget **A Saturday is data, not a shift (Nick, 2026-09-07; rule `saturdayShiftsFrom`, spec `reference_data.saturday_shifts`, effective 2026-09-01):** its sales, GWP, talk, referrals and cancellations count in every total, but it is never an Employed or Actual Shift nor a dialling day — Attendance (Actual ÷ Employed), SPD (Sales ÷ Actual Shifts) and the targets multiplied out of employed days are unmoved by Saturday work. Effective-dated so August's workbook-verified figures never change; guarded by `verify-saturday-rule.mjs`, which also proves the header Campaign/Team filters reach Month to date, Weekly and Daily. **A public holiday is data, not a shift either (Nick, 2026-09-25 — Heritage Day read as the floor's 18th shift; rule `publicHolidaysFrom` + `extraHolidays`, spec `reference_data.public_holidays`):** `dataOnlyDay()` is the ONE place that decides which days can never be a shift or a dialling day; the calendar is COMPUTED from the Public Holidays Act (`saHolidaysFor`, byte-identical in `agent/index.html`, never a table to extend); one-off holidays go in the spec's `extra[]` and `MTD_RULES.extraHolidays` together; rule check V25 fails on any shift landing on such a day and V25a warns on any day the floor was employed but nobody worked; `verify-public-holidays.mjs` guards all of it and, with `--live`, the published digest (it published a mean of each agent's own percentage, so a two-day joiner weighed the same as a full-month agent, in the very figure an agent is shown on their own card). **ONE NUMBER, ONE VERDICT (Nick, 2026-09-07; specs/agent-view-consistency-plan.md):** the engine decides, the page paints. Every comparison an agent sees (the R99 floor at the cent Salesforce books, the percent-to-target line, every rating chip) travels as a verdict in the payload — `worker/src/rules.mjs` is the one place the Worker derives a rule-book value, `portal.mjs` attaches `checks{value,volume}` and `thresholds.gwpFloorEx`, and `agent/index.html` never divides by VAT or carries a 99 again (`verify-rule-constants` fails on the literal). The rating row is the last five sessions and the two checks are the whole month — two windows, both true, never to be reconciled. `verify-agent-card.mjs` renders EVERY rated agent on the deployed page nightly and fails if one chip or verdict disagrees with the engine. A rule-book value changes only with a dated `_changes[]` entry in its spec file. **The Today tiles and the KPI drill-down are verdicts too (sprint 2026-09-29, D3):** ON TRACK / WATCH / FOCUS, what drives a KPI, the action and whether team-leader help is recommended are decided in `worker/src/drill.mjs` (record: `specs/kpi_drilldown_rules.json`, drift-checked by `verify-drill.mjs`) and travel as `me.drill`; the page's old `tileState` literals are gone and `verify-agent-card` asserts every tile equals its verdict. **Leave is data, not a shift — per agent (sprint 2026-09-29, D1; rule `excusedStatusFrom` + `excusedStatuses`, spec `reference_data.excused_statuses`, effective 2026-09-01):** an excused register status (AL, SL, FRL, ML, EAL whole-day; HDAL, HDSL, HDFRL half; Suspended/SUSP unavailable) with no talk and no sales leaves the agent's Employed Shifts — target pro-rated, Attendance and SPD untouched — while CA/UCA stay absences and a leave-marked day WITH activity keeps its shift and raises V26; an agent on leave all period stays in the head count; the digest carries `leave` and per-day `lv`; Ops shares the same list (`leaveCodes` + `leaveExcusedFrom`). Guarded by `verify-leave-days.mjs` and `verify-ops-leave.mjs`. **The campaign-manager view's figures (Spec Kit feature `specs/001-cm-view-signoff/`, 2026-10-01 — the CM sign-off list):** conversion = Σsales ÷ Σ**closed** leads (digest `closed` = every case closed in the period, any status; `null` when no case book is loaded — never 0%); average talk time shows hours against per-campaign targets in `specs/cm_rules.json` (Courtesy 5 h, Cuddle 4.5 h; a per-campaign Settings value overrides; every other campaign rides `cm:sla`); contact = a call whose status is not on `noContactStatuses`; the **billing month** is the 26th→25th cycle keyed by the month it ends in (`worker/src/cycle.mjs` is the one definition), BUILT by the engine and published by `tools/digest-republish.mjs` under `kv:agent-digest-cycle-YYYY-MM` — the live digest stays a calendar month; **Lead management excludes Courtesy at the REPORT layer only** (`MTD_RULES.leadReportExcludeCampaigns`, dated in the spec) so Courtesy's leads and closed leads still feed conversion. Guarded by `verify-cm-digest.mjs`, `verify-cm-signoff-worker.mjs`, `verify-cm-view.mjs`. **The Coaching Hub copy is refreshed in budgeted waves** (≤ 35 Hub calls per cron invocation — the FREE plan's 50-subrequest cap killed every wave silently from 2026-09-21 once the Hub reached 23 team leaders); every attempt is logged in `kv:coaching-wave-log` and a copy older than 26 h on a working day raises `coaching-stale` (`verify-coaching-wave.mjs`). **The live view is ALWAYS the current month (Spec Kit `specs/002-live-month-sync-coaching/`, 2026-10-01 — "we are in October, we need to see this month"):** before a month's first data the engine publishes an EMPTY-month payload (`empty:true`, every figure null, never zeros) and every view says "No <Month> figures yet" with a "<Previous month> (final)" link to its history key; the Worker refuses an empty payload over a same-month payload that has data (`empty_over_data`, emptiness derived server-side) and only staff roles may write the digest/report keys; the rollover grace still keeps any OLDER month off the live key. **Referrals refresh at 08:00 and 14:00 SAST every day** through the local tick (`tools/sync-referrals.mjs` → `kv:referrals-latest`, ingested by the headless digest and adopted by every PULSE tab when newer; a newer manual sync wins); runs are logged in `kv:referrals-sync-log` and a missed slot raises `referrals-slot-missed`. **Coaching belongs to the agent's current team leader** (by CB, whoever coached — "coached by Dalwin (SOS)"), lead-management coaching is counted and themed separately, and the copy is force-pulled daily from 05:30 SAST (`verify-empty-month`, `verify-referrals-schedule`, `verify-coaching-attribution`, `verify-live-month-page`).
13. **Accounts follow the Agent List, and the DATABASE enforces it.** The latest valid list is the single answer to "who is an agent": on the list ⇒ an active account with current details; off it ⇒ no account, no Agent View, not an active agent anywhere. That reconciliation is `sync_agent_list()` (supabase/migration-014), called by the Worker on every list publish and by the ten-minute cron, and it is **one transaction** — the previous JS loop of separate PostgREST calls could half-apply and leave leavers signed in, which is the whole reason it moved into Postgres. The Worker's job is now the fingerprint gate and PBKDF2 hashing (`worker/src/provision.mjs`); passwords are hashed there because Postgres cannot reproduce the WebCrypto scheme, so the function returns `NEEDS_HASHES` having written nothing and the caller re-calls — never teach pgcrypto a second password scheme. **A new agent's login is their CB number with `agentos123`, `apps:['agent']`, `tabs:{}` — no management app, ever.** Four guards, all fail-closed and all live in SQL now: a list under `p_min_roster` (25) is a broken pull not a walkout; deletions over `p_max_delete_share` (25%) are refused WHOLE; only `role='agent'` is ever deleted (no team leader is a roster row, so their absence proves nothing); a duplicate CB *inside* one list rejects the entire sync. `agent_list` holds every dated snapshot and `agent_sync_logs` names who left and when, so **removing an account never destroys history** — `auth_log` has no FK and survives; `app_sessions` cascades, which is correct, a leaver must be signed out. Read from `active_agents`, never from a private roster copy. **Team leaders are reported, never invented**: the list carries a leader's NAME and no CB, so a leader with no account (Hezron Pillay) is surfaced in `leaders.unrepresented` for a human — auto-creating one would mean inventing a login. There is deliberately no `agents` / `agent_views` / `agent_profiles` table and no Supabase Auth migration; the reasons are written at the top of migration-014 and are about not duplicating `app_users` or rewriting sign-in for all five apps. Guarded by `diagnostics/verify-agent-sync.mjs` (80 checks, run inside a transaction that always rolls back) and `tools/dry-run-provision.mjs` for a live PLAN. **THE FILE IS THE RECORD (2026-09-03, migration-020).** The "Download & Test" campaign was dropped from every publish for weeks because PULSE classified rows in the browser and posted only the ones it recognised — the database did its job on what it was given. So a station now posts EVERY row of EVERY sheet, unclassified (`rows`), and `publish_agent_list()` derives the roster in SQL (`campaign_label`: campOf's vocabulary + the VT-sheet fold), then runs `sync_agent_list` → `sync_team_leaders` → `sync_campaigns` in ONE transaction — a refusal at any stage rolls the earlier stages back, and the roster of record only moves on SUCCESS. Rows that do not become agents come back with the reason (`dropped[]`) and are kept in `agent_list_raw`. Campaigns nobody carries are DELETED (Nick), like agents and leaders; `campaign_sync_logs` is the history. Both apps adopt the returned record — what the browser classified is a preview. `agent_list_integrity` (list ↔ logins ↔ campaigns ↔ record) is read by the health cron every ten minutes and raises `agent-list-out-of-sync` in both apps while any row fails. Guarded by `diagnostics/verify-publish-agent-list.mjs` (45 checks, rolled back).
14. **A save must be acknowledged, noticed, and recoverable — and browser behaviour is only proven in a browser.** Born from 28–31 Aug 2026: PULSE's state save added `Content-Encoding: gzip`, the header wasn't in the Worker's CORS allow-list, and every browser silently refused to SEND the request for four days — no server log (the requests never arrived), only a transient toast, detected by client email. The standing rules (spec: `specs/save-reliability-plan.md`): **(a)** Node fetch proves nothing about CORS — any change to the headers or fetch options a browser client sends must pass `diagnostics/verify-cors-headers.mjs --live` before deploy, and a production deploy is not done until the post-deploy smoke (`verify-cors-headers --live` + `verify-live-save --live`, see the /deploy skill) passes in a real Chromium at the deployed origin. Widening the server allow-list never rescues a cached preflight (Max-Age 86400) — the client must be able to work without the new entry for 24 h; the Worker decides gzip by the magic bytes (1f 8b) precisely so no client needs the header. **(b)** Unsaved data is a STATE, not an event: both apps keep a dirty flag (`__vasDirtySince`/ack `__vasSaveOk` in PULSE; the shim's failed-save queue + `__cbxSaveOk` in Ops), show a persistent red banner past ~90 s, retry with backoff (30 s → 2 m → 5 m) so a failed save never waits for the user's next edit, and challenge `beforeunload` while dirty — never downgrade any of these to a toast. Guarded by `diagnostics/verify-save-acks.mjs` (16 checks; Ops half runs the GENERATED `site/index.html` because the save path lives only in the injected shim). **(c)** The server watches for what did NOT arrive: every acknowledged `/api/kv` POST lands in `kv_write_log`, and the cron's sentinel (`worker/src/health.mjs`, pure logic in `evaluateFreshness`) alerts when the upload manifest moves while neither state blob follows within the hour — activity-derived, never a fixed schedule, so a quiet Sunday raises nothing. Alerts live in `kv:health-alerts`, render as a banner in both apps, and CLEAR THEMSELVES when the condition ends. `store_freshness` (SQL view, named sentence-checks) is the queryable version; `verify-store-freshness.mjs` guards the logic. **(d)** The cron snapshots `vas-state` and `cb-config` daily (gzipped, 30 kept, `raw/kv-history/`) and `tools/restore-state.mjs` is the way back — it stashes the live blob before overwriting, so a restore is itself reversible.
15. **Large files take the Rake, not the browser (2026-09-08; specs/data-rake-README.md).** Anything the Upload Station cannot parse in-page — Power BI, open and closed cases past ~30 MB, the odd ViciDial pull — streams from the browser straight to Supabase Storage on a Worker-minted signed URL (`/api/upload/large/*`), is recorded in `upload_files` and queued in pgmq, and the GitHub runner's `tools/rake.mjs` turns it into a Parquet copy in `processed/` plus rows in the partitioned lake tables through the SQL merge functions (migrations 027–030). The Worker never carries the bytes and the browser never parses them. Two deliberate exceptions to older rules: CSP `connect-src` names the storage host (the one place the browser talks to Supabase, with a signed URL that grants one PUT to one path), and the lake is FULLER than the browser path (whole snapshots, zero-length calls, every charge line) — never "fix" the browser aggregates to match it. Closed cases key on the closure DAY at midnight UTC so both paths update one row (the first live load wrote 7,002 twins before migration-029); owners resolve through `rake_owner_map`, a name two agents share resolves to nothing, never a guess. ## Dashboard conventions (when editing the HTML)

- Everything configurable lives in `DEFAULT_RULES` / `DEFAULT_KPIS` and is user-editable at runtime — never hardcode a threshold that belongs in a rule. Reference rules from KPI filters as `$ruleName`.
- Snapshot sources (`snapshot:true`) REPLACE on upload; time-series sources APPEND and window by `_d`. Two supersede exceptions in confirmLoad: ATTENDANCE (new file wins per employee-day) and BI_ACTIVE_CASES (new file wins for its own Contract-Create-Date span — months accumulate).
- All user strings through `esc()`; names through `maskName()`; money through `fmtVal(v,'zar')`/`zarStack()`.
- New data sources = new entry in `SOURCES` (header contract) + `TRANSFORM` (canonical mapping) + optionally KPIs. Rejected rows must land in exceptions with a reason.
- Persistence goes through `store()`/`load()` (async `window.storage`). On Cloudflare a localStorage shim is injected by `tools/prepare-site.js`; the target backend is a Worker API over D1/R2 (plan Phase 2) — don't scatter new persistence paths.
- ZERO-LOCAL constraint (user requirement): no local LLM, no local watcher/daemon, no local database. Compute/AI/cron/login = Cloudflare (Worker, Workers AI Hermes 2 Pro, Cron Triggers, Access); data = Supabase (Postgres SQL + Storage; brain vault syncs to Obsidian via Remotely-Save S3). The Worker is the ONLY thing that talks to Supabase — service-role key is a Worker secret, never in browser code, and CSP connect-src stays 'self'.
- Session snapshot slots (SES_*) never mix into daily analytics.
